# Codex Remote 实用能力改进清单

初始复核日期：2026-10-04。问题基线：已部署的 Windows / Cloud / Web `1.15.0`，小程序 `2.1.3`，对应提交 `0e44d9c`。下文“现状”保留该基线的复核结果。P0 五项已在 `1.16.0` 实现并完成本机自动化及隔离原窗口验收，详细结果见 [P0 验收记录](codex-remote-p0.md)。真实弱网、电脑物理休眠、微信真机和 5G 仍待人工验收；P1 中的小程序核心能力已在小程序 `3.0.0`、配套 `1.17.0` 完成实现和本机自动回归，详见 [小程序重构说明](codex-remote-mini-program.md)。其他 P1、P2 项目继续按下文跟踪。

以日常工作的完整流程作为目标：找到原会话，完整读懂进展，继续发送，处理审批与队列，检查文件改动，取回成果；切换设备和断线后仍能准确恢复。参考 `codex-remote-bridge` 的实现与交互，但每项操作的数据来源和执行位置都必须是选中的目标电脑。

## 保留并继续完善的能力

- **原会话图片在网页显示**：图片由目标电脑读取，经认证 Cloud 中继传输，继续保留会话路径隔离；不把图片正文持久化到 Cloud。
- **浏览目标电脑的真实项目目录**：保留目录、文本预览、搜索和路径引用入口，继续沿用项目授权；目录内容确实来自被控电脑。
- **延续原 Codex 窗口**：继续使用原窗口自己的会话、任务、审批和队列。Cloud 只负责中继，Windows Service 与交互用户 Host 的职责保持清晰。
- **项目与独立聊天的收纳**：已有项目分组、展开/收起、收纳、排序和置顶，并在电脑端保存组织状态；后续补齐大量会话和跨端变化的处理。
- **网页的完整历史基础**：1.15 已移除此前 128 轮、80 条和 8000 字的截断，并支持分页直接阅读；后续重点是超大内容、读取效率和异常恢复。

## 复核证据的含义

“已复现”指本轮使用替代原窗口接口的受控浏览器场景复现；“源码确认”指实现中存在明确限制或处理缺口；“待实测”指需要真实桌面、网络或微信设备验证。受控场景没有提交真实任务，不代表手机、5G、休眠恢复或生产服务器已经验收。

### P0-1 状态、事件和重连一致

**现状：已复现。** 连接断开后，聊天标题仍可能显示“已同步”。新任务开始后，迟到的旧任务完成事件会短暂清除当前任务状态；后续读取才能纠正。前端状态快照与实时事件还缺少明确的先后版本约束。

**改动：** 分别显示连接状态、任务状态和最近一次同步结果；完成、暂停、引导等操作按会话与任务标识核对。重连后以原窗口状态恢复，并处理旧快照和迟到事件；非当前会话也更新侧栏状态。

**验收：** 断网后明确显示历史缓存；连续任务、旧事件迟到、桌面端停止任务、切换会话和重连时，状态及可用操作准确。已提交的任务不会因重连重发。

### P0-2 原窗口参数与下一次发送选择

**现状：已复现。** 用户在网页把模型从 `GPT-6.1-sol` 改为 `GPT-6`，历史更新后又被恢复成 `GPT-6.1-sol`。模型、思考强度和计划模式共用同一套刷新赋值逻辑。模型列表只保留模型标识，未利用原生参数能力信息。

**改动：** 分开保存原会话参数与用户为下一次发送作出的选择。首次进入按原窗口初始化；后台刷新保留尚未发送的选择。切换会话时重置继承关系，按原生模型能力提供有效参数。

**验收：** 输入期间连续刷新不改变用户选择；原窗口主动修改参数能够被识别；切换会话不串参数；发送到原窗口的实际模型、强度和模式与界面一致。

### P0-3 草稿、发送回执和结果不确定的处理

**现状：源码确认。** 切换会话要确认清空草稿，不能随时切出去再回来继续写。请求超时后恢复草稿并提示手动确认结果，但缺少明确的发送回执与查询入口。原窗口已接受、回执未到达的情况仍需防止用户重复提交。

**改动：** 按电脑和会话保留当前浏览器会话内的草稿、附件和参数；显示发送中、已接受、失败、结果待确认。使用稳定的提交标识，并结合原窗口能力确认提交结果后再允许重试。刷新后的草稿保留另行设计隐私与清理规则。

**验收：** 多会话切换不丢草稿、不串附件；接受后断线不会重复执行；未接受时能恢复输入；无法确认时清楚提示并提供查证入口。继续保持 Cloud 不保存聊天正文。

### P0-4 超大历史仍能完整读取

**已修复（1.16.1）。** 网页按需要缩小页数，大项或整轮自动分段还原，在原位置直接显示；不存在以导出文件代替查看的入口。断线续读、引用续期和跳至开头优先读取均已回归，见 [完整会话显示](codex-history-content.md)。

**改动：** 对超限页自动减少轮数；为超大单项提供自动分段读取并在原位置完整显示。历史读取显示进度、支持取消和继续，渲染保留滚动位置；用户直接在会话里阅读，避免为查看内容导出文件。

**验收：** 超过 128 轮、超过 16 MiB 的一页和单项内容均能完整获取；失败可继续且无缺项、重复或乱码；阅读旧消息时新输出不把位置拉走。保留传输和中继内存边界。

### P0-5 审批、队列和停止任务的真实恢复验收

**现状：待实测。** 已有原生审批、引导、停止和队列接口；1.14 有真实任务/审批记录，1.15 有受控流程和真实只读检查。弱网、浏览器后台、电脑休眠，以及桌面先处理审批后的恢复还需专项验收。

**改动：** 补齐失效审批、重复点击、权限变化和控制页占用的明确反馈；恢复时重新读取当前审批与队列，按真实任务标识处理。原窗口接口变化时检查能力并说明原因。

**验收：** 同一审批只生效一次；桌面已处理的审批不会继续等待；停止针对当前任务；队列增改删与桌面一致；断线、休眠和授权变化后不会执行过期操作。使用隔离项目完成真实流程，明确记录设备与网络条件。

## P2：按使用需求扩展

- **自动化管理**：创建、编辑、暂停、删除和运行结果。必须明确目标电脑的调度、在线要求与权限，不能只复制参考项目的配置页面。
- **插件、应用、MCP 的完整管理**：安装、启停、配置和 OAuth。敏感授权与账号操作保留目标电脑侧的清晰边界，先补状态和可恢复的错误提示。
- **更完整的开发工具**：分支/工作树管理、交互终端、文件补丁撤销/重做；按日常需求逐项开放。远程终端必须执行在目标电脑，支持断线恢复和权限核对。
- **语音及其他便利功能**：语音输入、快捷键扩展等，在核心流程稳定后安排。

## 系统实现约束

原窗口是会话、任务、审批和队列的权威来源；网页与小程序维护可恢复的展示状态。目标电脑是文件、图片、Git 和执行的实际来源；中继服务器的本地目录或 Runtime 不能替代它。参考项目的一些辅助接口直接使用服务器本地目录，迁入 LanPower 时要逐项核对执行位置。

后续增强继续保留：开发与项目授权、Service 到交互 Host 的受保护边界、Cloud 有界内存中继、正文不持久化、不在日志输出内容与凭据、重连不重发任务。项目组织状态可以保留在电脑端；与官方桌面组织状态一致的部分，应通过可靠接口实现，并说明暂时由 LanPower 单独管理的字段。

## 建议实施顺序

1. 先修 P0-1、P0-2、P0-3，使状态、参数和发送可信。
2. 完成 P0-4 和 P0-5 的大历史与真实控制恢复验收。
3. 补全聊天库、文件上传/下载、改动审阅及小程序核心能力，保留图片与目录优势。
4. 按实际使用需求增加 P2 功能。

每批独立验收后更新版本与本机 Docker / Windows 应用；远程仓库和正式云服务器仍按用户明确要求同步。
