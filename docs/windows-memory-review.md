# Windows 客户端内存检查（2026-09-30）

本轮仅检查已运行的 Windows 客户端、源码与发布产物，未修改应用代码、运行配置或安装文件，未重启或结束桌面端和服务。结论是桌面端仍有优化空间，优先检查托盘状态下的窗口生命周期与页面创建方式。具体降幅需要实施后的对照测量，不能仅凭任务管理器截图承诺。

## 测量对象与口径

- 已安装桌面版本为 `1.4.0.0`，EXE 的 SHA-256 与本地 `windows/out/desktop-delivery/source/windows/out/desktop/` 交付产物一致。
- 对照检查时的源码提交 `998dca5`：桌面项目的两个 XAML、应用入口、窗口辅助代码、管道客户端及项目文件与交付快照一致；`MainWindow.xaml.cs` 唯一差异是状态刷新间隔，交付快照为 **20 秒**，当前源码为 **5 秒**。本轮实测对应已安装的 20 秒版本。
- 通过 Windows 窗口枚举确认主窗口仍存在，但不可见且没有最小化；采样对象处于窗口隐藏状态。没有主动打开窗口、切页或显示二维码。
- Windows 进程计数器每 10 秒采一次，共 19 次，持续约 181 秒；随后使用 `dotnet-counters` 每 2 秒采集一次桌面端运行时计数器，共 30 次、约 1 分钟。
- 下表统一使用 MiB（1,048,576 字节）。截图中的内存列与私有工作集数值接近。总工作集包括共享驻留页；私有提交量包含不一定正在物理内存中的已提交私有页，不能相加，也不能直接与截图的单列比较。[Windows 工作集说明](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set)

## 已确认的优化候选

| 顺序 | 当前实现与证据 | 可评估的调整 | 收益与约束 |
| --- | --- | --- | --- |
| 1 | `MainWindow.Shell.cs` 的 `OnClosing` 调用 `Hide()`；`App.MainWindow` 继续持有完整窗口。状态与二维码计时器只在 `OnClosed` 停止 | 隐藏后暂停界面更新，托盘状态使用较低频率刷新；无二维码时停止倒计时 | 减少持续分配与后台工作；仅停止计时器不会释放完整 WPF 基础开销 |
| 2 | `MainWindow.xaml` 同时声明六个页面，导航仅切换 `Visibility`；`InitializeComponent()` 一次创建这些对象 | 页面首次访问时创建；评估隐藏后释放可重建页面或窗口 | 减少长期保留的控件与关联资源；必须保留输入、配对进度和偏好，恢复窗口时立即读取新状态。具体收益尚未测量 |
| 3 | 每次 `ApplyStatusDisplay()` 调用 `StateBrush()` 新建四个画刷，并重新设置界面属性 | 共享冻结的状态画刷，状态变化时才更新相关属性 | 属于减少小对象分配的优化，不能据此承诺大幅降低常驻量。[WPF 对象优化说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-object-behavior) |
| 4 | 桌面项目同时启用 WPF 与 Windows Forms；`App.xaml.cs` 使用 `NotifyIcon` 和 `ContextMenuStrip` 提供托盘 | 如目标是明显降低长期后台占用，可评估独立轻量托盘，仅在需要时运行完整 WPF 窗口 | 同一进程销毁窗口仍可能保留框架与渲染资源；独立托盘方案涉及单实例激活、状态保存与窗口重建，改动范围更大。替换托盘库本身的收益未经测量 |

窗口对象已经执行 `Hide()`，但没有被销毁，六个页面依旧被窗口引用。WPF 与图形相关模块也确实已加载，包括 `wpfgfx`、`PresentationNative`、Direct3D 和显卡驱动模块；模块存在不能证明某个模块独占了多少私有内存。

## 已有控制与优化边界

- 日志由 `ServiceLog.ReadTail()` 限定返回最近 80 行，桌面只在进入日志页或点击刷新时读取；未发现桌面不断追加全部日志的实现。
- 二维码在切页、窗口隐藏或超时后清除图像引用；加载使用 `BitmapCacheOption.OnLoad`、关闭流并冻结位图。此处已具备资源释放措施。
- 状态请求有防重入，管道、读写流和 `JsonDocument` 均使用 `using`；未发现这些请求对象在每次刷新后被主动加入长期集合。
- 桌面交付运行时配置未启用 Server GC，不能直接套用“关闭 Server GC”解释桌面端占用。
- 自包含 EXE 的文件大小不能直接代表运行时占用。WPF 当前也不支持把 `PublishTrimmed` 当作简单的裁剪开关；打包或运行时参数若要调整，应单独测量兼容性和收益。[单文件发布说明](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview)、[WPF 裁剪限制](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)

现有产品已提供无需改代码的选择：配对完成且暂时不需要界面时，可在托盘右键菜单选择“退出界面”。该操作退出桌面进程，后台服务继续负责 LAN / Cloud；以后可重新打开桌面。普通关闭默认只隐藏窗口。本轮只确认现有实现，未替用户执行退出操作。

## 后续验证方法

后续若实施优化，使用相同发布方式、同一运行时和相同数据，对比启动后、浏览六页后、收起托盘后及多次恢复窗口后的私有工作集、私有提交量、托管堆和分配率。延长空闲观察时间，并检查自然 GC 后的变化；同时复验托盘状态、重复启动激活、二维码清除、配对进度和服务连接。

本轮未采集包含应用数据的内存转储，未强制 GC 或清空工作集，也未执行电源动作。采样结束时原桌面端和服务仍在运行。最小验证为实际进程采样、交付产物哈希和源码差异核对、检查文档链接及 Git 差异；没有运行会写入实际服务的演练。
